Data acquisition options for historical and
upcoming NRL team lists and squad
announcements
Executive summary
Primary,  lowest-friction  acquisition  comes  from  the  official  NRL  website’s  own  structured  payloads
embedded in HTML. The draw and ladder pages expose JSON in q-data attributes (#vue-draw, #vue-
ladder) that can be scraped without a headless browser , and those payloads include per-match match-
centre URLs for downstream capture. 
Historical and upcoming team lists are best treated as “versioned documents”, not single facts. The official
“Team Lists” topic hub provides a canonical stream of Tuesday team-list articles and game-day “Late Mail”
updates, each with its own publish timestamp. 
Terms matter . The official Terms of Use explicitly constrain use of NRL digital platforms to “personal, non-
commercial use” and restrict reproduction without written consent, which is a practical trigger for licensing
if your prediction system is commercial or redistributed. 
For structured, ID-rich data (player IDs, team IDs, schedule IDs) and operational stability, commercial feeds
(notably Stats Perform as the league’s official data partner) are the cleanest path. 
A pragmatic build order is: (1) fixtures via q-data draw; (2) team-list URLs via the “Team Lists” topic page
plus  sitemap  crawling;  (3)  parsing  team-list  articles  into  a  normalised  “named  17/extended  squad  +
timestamp + source”; (4) monitoring and diffing for late changes; (5) only then add redundancy (club sites,
media, community archives) and/or licensed feeds.

Competition IDs used by official NRL draw/ladder parameters
The draw/ladder endpoints use a  competition query parameter . A practical mapping (used by  nrlR)
includes 111 → NRL and IDs for State of Origin and other comps. This is useful when you want to monitor
multiple competitions consistently (NRL, NRLW, Origin). 
Commercial and licensed feeds
Commercial feeds become attractive when you need (a) stable IDs across years, (b) guaranteed uptime and
SLAs, (c) explicit rights to use the data in a product, and (d) richer metadata (team lists as structured objects,
player IDs, injury status, late swaps) than you can reliably infer from web pages.

Implementation guidance for data acquisition
Discovering historical team list URLs (2012–present)
Sitemap-driven enumeration is the most robust way to backfill 2012–present because it doesn’t assume
today’s topic pages include older content.
NRL  publishes  a  sitemap  location  in  robots.txt,  which  gives  you  a  stable  starting  point  for  URL
discovery. 
The sitemap index itself references multiple gzipped sitemap shards and a current.xml.gz feed (useful
for incremental monitoring). 
A practical backfill strategy is to download each referenced .xml.gz, extract URLs, and filter by patterns
like: - /news/ AND (team-lists OR late-mail), for the official team list and late change articles. 
For upcoming rounds, the “Team Lists” topic hub is your highest-signal feed for new team list pages and
late mail entries. 
Scraping strategies for JS-driven pages
The single best tactic on NRL pages is to  avoid rendering and instead  extract embedded JSON when
present.
Fixture and match-centre URL discovery can be done by reading the  q-data attribute on  #vue-draw
from  the  draw  endpoint:  -  https://www.nrl.com/draw/?competition={comp}
&round={round_number}&season={season} -  Parse  q-data into  JSON.  -  Read
fixtures[*].matchCentreUrl to build match-centre URLs. 
Ladder extraction works the same way via #vue-ladder and its q-data. 
Team list articles themselves are scrape-friendly HTML pages. The nrlR implementation demonstrates a
selector-based approach that identifies each game header (match-header) and then reads  li.team-
list items to extract home/away player names and roles. 
Some pages appear to be JS-driven without embedding  q-data in the initial HTML. The Casualty Ward
page shows templated placeholders and error messaging in the HTML served to non-JS clients, which
strongly suggests the data is loaded from an API call at runtime. 
When a page behaves like Casualty Ward, there are three escalating options: 1.  Reverse-engineer JSON
endpoints by capturing network calls once (browser devtools) and then reproduce them with requests
plus caching and headers. 2. Use a headless browser only for the “API discovery” step, then revert to direct
JSON calls. 3. If the endpoint is private or volatile, fall back to scraping the linked injury-news articles, which
are stable HTML pages.

Entity resolution and IDs
Stable IDs are the main difference between “a scraper that works today” and “a dataset you can train on for
2012–present”.
If you consume the Champion Data JSONs, playerId is included alongside player names (firstname, 
surname, displayName), and fixtures provide matchId, homeSquadId, and awaySquadId. This is
the fastest route to a consistent cross-season identity graph, assuming you have the rights to use the data.
If  you  scrape  team  list  articles,  you  should  assume  you’ll  initially  see  only  names  and  roles.  A  robust
resolution strategy is: - Create a canonical player table with your own surrogate key. - Attach multiple
external identifiers when you have them (e.g., Champion Data playerId, NRL player-page slug, historical
aliases). - Maintain an alias table (name_variant,  from,  to,  effective_dates) for spelling and
diacritics  (e.g.,  apostrophes).  This  is  motivated  by  the  fact  that  public  sites  mix  display  names  and
abbreviated forms. 
Timestamping, versioning, and change capture
Team  list  data  is  inherently  versioned.  Your  storage  should  preserve:  -  source_url -
source_published_at (from the article’s timestamp where available) - scraped_at - raw_html (or
raw  JSON)  -  parsed_payload (normalised  roster  object)  -  content_hash and/or
diff_from_previous
Because NRL Terms of Use explicitly reserve the right to modify the network and content, and note that
availability is not guaranteed, you should treat breakage as normal and engineer for easy reprocessing. 
Handling template drift
Template drift is easiest to manage if you test parsers against representative pages from different eras: -
modern round team lists (e.g., 2025 and 2026 examples), - late mail pages from finals, - and at least one
older team list page once your sitemap backfill finds them. 
Unit-test  the  parsing  logic,  and  keep  a  “known-good  HTML  fixture”  corpus.  The  nrlR package  itself
includes tests for fixtures, ladders, and lineups, which is a useful pattern to emulate even if you write your
own pipeline.

Practical scheduling design for “Thursday/24h/final-17” inference
A match-centric schedule works better than a single weekly cron, because the round spans multiple days.
A minimal schedule is: - Initial capture: when the official team list article is published on Tuesday (widely
reported as “Teamlist Tuesday”, commonly 4pm; use as a starting heuristic). 
-  Pre-match refresh: run an automatic refetch and diff at a fixed offset (e.g., 24 hours pre kick-off per
fixture), using the fixture kickoff time from draw q-data. 
-  Final  refresh:  refetch  shortly  before  kick-off  (e.g.,  60–120  minutes)  and  on  kick-off  for  a  definitive
snapshot. This is where match-centre parsing (if feasible) usually produces the cleanest “final 17” record,
because it is aligned to the game object rather than a news article. 
When  official  sources  fail  or  lag,  you  can  cross-check  with  secondary  round  aggregators  (media  or
community), but treat them as non-authoritative and record provenance. 
Automation mechanics: diffing, webhooks, and polling
Diffing  should  operate  on  a  canonical  representation  (e.g.,  team_id,  player_id,  named_slot, 
status) rather than raw text, so that formatting edits don’t look like roster changes.
For event propagation: - Convert “diff detected” into a webhook call to your model-inference service (or
queue message). - Keep a human-readable “change log” for auditability (“Player X moved from 18th to 14;
player Y omitted”). 
If you adopt RSS/Atom feeds (where available), WebSub is a standard pattern to push updates rather than
poll, but it depends on the publisher supporting it. 
Prioritised checklist of minimum viable sources and add-ons
A minimum viable, mostly-official pipeline can start without any headless browsing.
First  build:  -  Pull  fixtures  and  match-centre  URLs  from  https://www.nrl.com/draw/?
competition={comp}&round={round}&season={season} by extracting #vue-drawq-data. 
- Pull team list URLs from  https://www.nrl.com/news/topic/team-lists/ and then scrape each
team-list article into a structured roster snapshot. 
- Backfill history by crawling NRL sitemaps (discover via robots.txt → sitemap index → gz shards) and
filtering for team-lists and late-mail URL patterns.
